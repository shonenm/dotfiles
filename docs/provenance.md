# 構成要素の由来

> **由来:** **Configuration** このリポジトリの文書化規則

この文書は、dotfiles 内の要素が一般的なツール、外部プラグイン、ローカル実装のどれに当たるかを判断するための共通ルールである。

## 区分

| 区分 | 意味 |
|---|---|
| Upstream | GNU Stow、tmux、Neovim、Piなど、外部で提供される本体機能 |
| Plugin | TPM、lazy.nvim、Pi packageなどを通じて導入する外部拡張 |
| Configuration | UpstreamやPluginを選択・設定・連携する、このリポジトリの設定 |
| Custom | このリポジトリで実装・保守するスクリプトや拡張 |
| Local patch | UpstreamやPluginの不足を補う一時的なローカル変更 |

「Configuration」「Custom」はリポジトリ内での保守責任を表す。第三者コードの著作権やライセンス上の出自を断定する表示ではない。

## 表示方法

各詳細文書のタイトル直下に、その文書で扱う要素の由来を表示する。

```md
> **由来:** **Upstream** tmux本体 / **Plugin** TPM導入物 / **Configuration** `common/tmux/` / **Custom** `scripts/tmux-*`
```

この文書には機能別一覧を置かない。由来の表示は機能を説明する詳細文書を正本とし、キー操作、挙動、プラグイン名、設計理由と一緒に更新する。これにより、由来だけを集約した台帳との二重管理を避ける。

## 判定ルール

- `common/`、`mac/`、`linux/`は由来ではなくStowの配置単位であり、外部ツールの設定とCustom実装の両方を含む。
- `scripts/`と`common/pi/.pi/agent/extensions/`は原則Customとして扱う。
- package managerやplugin managerから取得される本体コードはリポジトリに含めず、各設定ファイルの宣言を導入元の正本とする。
- 外部機能をローカルで上書きする場合はLocal patchとし、対象、理由、削除条件を対象分野のpatch文書に記録する。
- 複数の区分を含む文書では、区分ごとに対象を短く併記する。

## 更新ルール

1. 新しい機能を文書化するときは、詳細文書のタイトル直下に由来を記載する。
2. 既存機能の由来が変わったときは、その詳細文書だけを更新する。
3. 新しい区分やリポジトリ全体の判定ルールが必要な場合だけ、この文書を更新する。
4. 外部コードをリポジトリへ直接取り込む場合は、ファイル先頭または同じディレクトリのREADMEに元URL、基準version、ローカル変更を記録する。
